# Ludex integration depth: what can really sync

Date: 2026-10-06
Status: primary-source documentation review. No credentials were issued, accounts connected, APIs called, or provider payloads tested. This report supplements [progress-sync-feasibility.md](progress-sync-feasibility.md); it does not change that report or claim a connector is already implemented.

## Product recommendation

Make Ludex the durable, cross-service record of a person’s entertainment life. Provider integrations should contribute observations to that record; they should not own or silently overwrite it. Keep four things distinct in the data model and UI: a title in the library, a user-authored log, a provider observation, and an activity the user chose to publish to friends.

For the first genuinely useful integrations, prioritize:

1. **Steam** for opt-in library import, recent playtime, current-game presence snapshots, and game-published achievements.
2. **Trakt** for user-authorized movie/episode history, playback position, scrobbling for compatible players, and correction/import workflows.
3. **Plex webhooks** for near-current playback events from self-hosted libraries. Add **Kodi + Trakt** as the supported-player route that covers a different installed-player audience.
4. **Jellyfin** as an advanced connector, using its webhook plugin when the server owner can configure it or a local companion for the user’s own session.
5. **Where-to-watch** as a separately licensed catalog feature. Pilot TMDB’s JustWatch-backed country availability for a non-commercial prototype; compare Watchmode for commercial use and mobile deep links before launch.

Treat Xbox as a technically documented but gated experiment, not as impossible and not as launch-ready. Keep PlayStation and Nintendo manual until first-party consumer access is established. Epic and GOG documentation reviewed here describes title/game-integrated SDK functionality rather than a broad consumer account API for an unrelated third-party library.

### Steam: make presence useful without calling it a start event

Valve documents `GetPlayerSummaries`, `GetRecentlyPlayedGames`, `GetOwnedGames`, `GetPlayerAchievements`, and `GetSchemaForGame`; public profiles and privacy settings determine whether game data is returned. The Steam help center defines “Game details” visibility separately from basic profile visibility. Steam’s `GetPlayerSummaries` is the right public profile/presence check to prototype, while `IPlayerService` gives the recent/owned game snapshot and playtime fields. The Steamworks native SDK can return `achieved` and `unlocktime`; the Web API documentation for `GetPlayerAchievements` only promises the list of achievements unlocked and does not establish that same timestamp in the public Web API payload. [GetPlayerSummaries](https://partner.steamgames.com/doc/webapi/ISteamUser), [IPlayerService](https://partner.steamgames.com/doc/webapi/IPlayerService), [Web API achievements](https://partner.steamgames.com/doc/webapi/ISteamUserStats), [native SDK unlock time](https://partner.steamgames.com/doc/api/ISteamUserStats#GetUserAchievementAndUnlockTime), [Steam privacy settings](https://help.steampowered.com/en/faqs/view/1150-C06F-4D62-4966).

The official method URLs are `https://partner.steam-api.com/ISteamUser/GetPlayerSummaries/v2/`, `https://partner.steam-api.com/IPlayerService/GetRecentlyPlayedGames/v1/`, `https://partner.steam-api.com/IPlayerService/GetOwnedGames/v1/`, `https://partner.steam-api.com/ISteamUserStats/GetPlayerAchievements/v1/`, and `https://partner.steam-api.com/ISteamUserStats/GetSchemaForGame/v2/`. Valve’s documented `GetPlayerSummaries` example explicitly includes `steamid`, `communityvisibilitystate`, `profilestate`, `personaname`, `lastlogoff`, profile URL, and avatar URLs; the page notes a 100-SteamID batch maximum. The example does not show optional current-game fields, so treat common `gameid`/`gameextrainfo` presence as a response capability to validate, not a guaranteed field contract. `IPlayerService` describes visible owned games, recently played games, and name/icon inclusion; its response schema should also be confirmed against an authorized account before locking the internal import format. `GetPlayerAchievements` promises a list of unlocked achievements, with `GetSchemaForGame` for the game’s achievement definitions. The separate native SDK method `GetUserAchievementAndUnlockTime` explicitly returns `pbAchieved` and `punUnlockTime` (Unix epoch; zero can mean an unlock predating Steam’s tracking). That is timestamp provenance from the native game-facing API, not evidence that the public Web API returns the same field. [GetPlayerSummaries](https://partner.steamgames.com/doc/webapi/ISteamUser), [IPlayerService](https://partner.steamgames.com/doc/webapi/IPlayerService), [Web API stats](https://partner.steamgames.com/doc/webapi/ISteamUserStats), [native SDK unlock time](https://partner.steamgames.com/doc/api/ISteamUserStats#GetUserAchievementAndUnlockTime).

Standard Steam user keys require a Steam account, an associated domain, and agreement to the Web API Terms. Valve’s terms say Steam Data may be distributed to end users for personal use through the registered application; the key is personal to that application, must be kept confidential, and authorizes retrieval only as requested by the user. The terms also state a 100,000-call daily cap, allow Valve to change or terminate access, and require a privacy policy for nonpublic data. For a monetized Ludex launch, confirm that the intended product and data presentation fit the current terms. Steam OpenID is identity proof, not broad OAuth consent. Never ask for or store Steam passwords. A dedicated Ludex server key stays server-side. [Key setup](https://partner.steamgames.com/doc/webapi_overview/auth), [Steam Web API terms](https://steamcommunity.com/dev/apiterms), [OpenID](https://steamcommunity.com/dev).

At scale, batch profile summaries in groups of up to 100 SteamIDs, cache them, stagger polls, and avoid polling every Ludex user continuously. As an illustration, 10,000 distinct watched profiles polled every five minutes need about 28,800 summary calls/day when perfectly batched; 100,000 profiles would exceed Valve’s documented daily cap. This is a capacity calculation, not measured Ludex traffic. Poll a user’s own account on demand and friends’ presence only when both sides opt in; keep library/achievement snapshots on a slower schedule. [GetPlayerSummaries batch limit](https://partner.steamgames.com/doc/webapi/ISteamUser), [Valve’s daily call limit](https://steamcommunity.com/dev/apiterms).

**Recommended Steam UI:** connection status, last library sync, separate “Share current game with friends” switch, and an audience/spoiler choice for imported achievements. Show a current title as “Steam says playing · checked 2 min ago.” If Ludex compares successive polls, call it “Ludex noticed play activity,” never “started now.” A one-poll transition cannot prove exact start time or intentional gameplay. Let users hide individual games even when Steam makes them visible.

### Trakt, Plex, Jellyfin, and Kodi: separate history from scrobbling

Trakt’s model is unusually useful because it distinguishes **history** (watched movies/episodes and repeated viewings), **watchlist**, and **playback progress**. An app can authorize through PKCE; device flow is suited to TV/media-center setup. A Trakt player can submit start, pause, and stop progress, and an authorized app can read history/playback to restore progress. The current sync guidance recommends caching last-activity timestamps and checking what changed instead of repeatedly downloading full history. The current documented authenticated limits are 500 GETs per five minutes per user and one write per second per user; handle `429` and `Retry-After`, and avoid sync loops. [Trakt concepts](https://developer.trakt.tv/), [OAuth](https://developer.trakt.tv/docs/authentication-oauth), [sync/scrobble/history](https://trakt.docs.apiary.io/reference/sync), [incremental sync](https://trakt.docs.apiary.io/reference/sync#last-activities), [limits](https://developer.trakt.tv/docs/rate-limiting).

Trakt’s updated API policy permits apps that manage a user’s own history and media-player integrations that scrobble with authorization; it also permits a user choosing to share their own activity. It prohibits bulk harvesting, resale, and redistributing community data as a general feed. Build Ludex’s friend feed from Ludex posts or from activity a user deliberately publishes through their own connected account; do not import the friends graph/history from Trakt to seed Ludex’s social graph. Trakt also says unused app registrations can be removed after 30 days without use, so keep the integration active and monitor developer notices. [Current Trakt API-use policy](https://developer.trakt.tv/docs/api-use-policy).

Plex is attractive because its server-side webhook can POST playback events without Ludex polling a Plex account. The official Plex Webhooks feature has a Plex Pass requirement and is configured by the server owner; the destination must be reachable from the server. Jellyfin’s official webhook plugin lets a server administrator select event types, destination, and user filter. For both, treat webhook messages as at-least-once observations even if the provider does not promise delivery semantics: make receipt idempotent, record received time, and provide a connection health page. Do not claim an external provider’s push is instantaneous or guaranteed. [Plex setup](https://support.plex.tv/articles/115002267687-webhooks/), [Jellyfin webhook plugin](https://github.com/jellyfin/jellyfin-plugin-webhook).

For privacy, a local companion can be the safer bridge for a self-hosted Jellyfin/Kodi server: it holds a user-authorized server token locally and sends only normalized title ID, event type, observed time, playback position, and a source identifier to Ludex. But it adds installation, updates, and networking support. A server webhook plugin is easier to configure for people who already expose their server externally; a local agent is better where the library must remain LAN-only. Make these separate advanced paths instead of turning connection setup into a firewall tutorial.

### Xbox correction: endpoint exists, consumer connector still needs validation

The prior feasibility summary grouped Xbox with platforms lacking a public consumer API. That is too broad. Microsoft publishes `GET https://achievements.xboxlive.com/users/xuid({xuid})/achievements` for a user’s list, and `GET https://achievements.xboxlive.com/users/xuid({xuid})/achievements/{scid}/{achievementid}` for one achievement. The latter schema includes `progressState` and `progression.timeUnlocked`; its auth page requires an authenticated XBL token and documents a third-party-site privacy row (public visibility allows access; friends-only/blocked do not). Microsoft’s title-website flow is: Entra app registration for personal Microsoft accounts; OAuth authorize at `https://login.microsoftonline.com/consumers/oauth2/v2.0/authorize` with `xboxlive.signin` (optional `xboxlive.offline_access`); token exchange at `https://login.microsoftonline.com/consumers/oauth2/v2.0/token`; Xbox user token at `https://user.auth.xboxlive.com/user/authenticate`; then XSTS at `https://xsts.auth.xboxlive.com/xsts/authorize`. Microsoft says this usually gives read-only access to Xbox services data, but the docs are still framed around title websites/GDK. These are real official technical routes. The unresolved product question is whether Ludex, as an independent consumer library, can register and use this path in production under Microsoft’s current service rules. Run a small permission/registration feasibility spike before treating it as a roadmap commitment. [Website authentication and exact flow](https://learn.microsoft.com/en-us/gaming/gdk/docs/services/fundamentals/s2s-auth-calls/service-authentication/live-website-authentication?view=gdk-2604), [achievement access/privacy/schema](https://learn.microsoft.com/en-us/gaming/gdk/docs/reference/live/rest/uri/achievements/uri-usersxuidachievementsscidachievementidget?view=gdk-2604), [list endpoint](https://learn.microsoft.com/en-us/gaming/gdk/docs/reference/live/rest/uri/achievements/uri-achievementsusersxuidachievementsv2?view=gdk-2510).

### Where to watch: coverage, links, and the business-model gate

TMDB’s watch-provider endpoint returns subscription/rent/buy availability by country, powered by JustWatch. TMDB explicitly says it does not return full deep links; it returns enough information to show availability and links back to TMDB, and JustWatch attribution is mandatory. TMDB’s API is free for non-commercial use with attribution; commercial use requires a separate written agreement, and it currently says it does not provide an SLA. This is a sensible prototype input, not a complete commercial “watch here” promise. [TMDB TV watch providers](https://developer.themoviedb.org/reference/tv-series-watch-providers), [TMDB FAQ and commercial terms summary](https://developer.themoviedb.org/docs/faq), [API terms](https://www.themoviedb.org/api-terms-of-use).

Watchmode’s official API documents region lists, country-filtered streaming sources, source type (`sub`, `rent`, `buy`, `free`, `tve`), web URLs, iOS/Android deep links, and episode-level sources. Its docs say deep links and episode links are paid-plan features; its public pricing currently labels its free Developer plan non-commercial and the Startup plan commercial, with a displayed price of **US$349/month** at retrieval on 2026-10-06. Recheck pricing, country coverage, credit cost, permitted caching, attribution, and whether its data covers Ludex’s launch markets before budgeting or committing. Availability can be stale or wrong; its own API page says so. [Watchmode API docs](https://api.watchmode.com/docs), [regions endpoint](https://api.watchmode.com/docs), [pricing](https://api.watchmode.com/), [API terms](https://api.watchmode.com/tc).

Design “Where can I watch?” as a country-aware utility: ask for region once, allow changing it per search, show provider and plan category, label the data refresh time, and send the user to a provider/TMDB link. Never imply the subscription is included, that the title is playable in the user’s exact plan, or that the listing is current. For group decisions, intersect provider availability by each friend’s selected services, not account credentials.

### Browser extensions and cross-app activity

A browser extension can make logging delightful: a user clicks Ludex while on a supported title page, the extension reads that page’s visible title/episode and offers “Add to watchlist,” “Log episode,” or “Share.” It cannot be a universal streaming observer. Each service’s site markup can change, users must grant host access, and an extension content script has access only to pages it is authorized to run on. Chrome’s Manifest V3 service worker is event-driven and can stop when idle, so it is not a reliable always-running scrobbler. Store policies require transparent disclosure of browsing-data collection and constrain it to what the user-facing feature needs. Avoid extracting player internals, protected media, cookies, passwords, or hidden service APIs. [Chrome host/content-script permissions](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts), [service-worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle), [Chrome Web Store user-data policy](https://developer.chrome.com/docs/webstore/user-data).

A useful extension is a **log shortcut** that only reads the active tab after a click and sends a small candidate title to Ludex for the user to confirm. If a browser site exposes `MediaSession` metadata or a stable visible episode title, that can improve matching, but it still does not establish playback completion. Keep this enhancement optional, per-site, visibly enabled, and separate from provider-supported sync.

Steam rich presence is also not generic game telemetry. Steam’s enhanced rich presence is data set by a game through its Steamworks SDK. Discord’s Social SDK describes game activity as something a game publishes to Discord and only exposes the activity associated with the current game inside the game SDK; Discord bot presence access is separately a privileged guild intent. Therefore, arbitrary PC game telemetry cannot be collected by asking Discord to report every friend’s current game. [Steam rich presence](https://partner.steamgames.com/doc/features/enhancedrichpresence), [Discord Social SDK activity](https://discord.com/developers/docs/social-sdk/classdiscordpp_1_1Activity.html), [Discord privileged intents](https://support-dev.discord.com/hc/en-us/articles/6207308062871-What-are-Privileged-Intents).

## Sync design that protects a person’s library

### Store facts with provenance

A robust cross-provider record needs a canonical catalog item, provider-to-catalog bindings, and an event ledger. An event should retain its source (`manual`, `steam_snapshot`, `trakt_history`, `plex_webhook`, `jellyfin_webhook`, etc.), provider event/record ID when one exists, observed time, event time if the provider supplies it, payload hash, match confidence, and correction/retraction state. Store OAuth/API tokens separately in encrypted secret storage and never put raw credentials in activity content.

This makes it possible to say “Steam last saw you in this game two minutes ago,” “Plex sent an episode-stop event,” or “you marked this episode watched manually.” It also prevents a resume checkpoint from becoming a viewing completion and prevents an achievement from being misrepresented as finishing a game’s story.

### Connect, import, correct, disconnect, reconnect

1. **Connect:** explain exactly which fields the source exposes, which are hidden by privacy settings, how often Ludex checks, and whether setup must happen on a PC/home server. Ask separately for library import and friend-feed sharing.
2. **Preview import:** match provider IDs to canonical titles, group likely duplicates, mark uncertain editions/remakes/episodes for review, and let users choose which years or activity to bring over. Historical imports are quiet by default: they fill the library but do not cause old feed posts or notifications to appear.
3. **Merge:** deduplicate provider records by stable external ID plus item/episode identity and event ID. For sources without event IDs, use a conservative fingerprint including source, user, media ID, action, and time window. A repeated webhook or repeated sync updates the same imported observation.
4. **Correct:** preserve edits made in Ludex. If a provider correction/revocation conflicts with a manually confirmed Ludex log, mark the imported assertion retracted and show the difference; never silently erase the user’s own note, rating, collection, or manual log.
5. **Disconnect:** revoke/delete stored provider credentials and stop future reads immediately. Keep the user’s Ludex library and user-authored history. Offer a distinct “remove history imported from this source” action; users should not have to delete their library to disconnect one connector. Reconnecting can resume existing mappings and checkpoints, with a choice to backfill the gap or only sync forward.
6. **Delete account:** provide a separate account-level export/deletion path and delete provider copies according to documented policy. Deleting a connector is not the same as deleting Ludex.

### Freshness language and feed rules

Use a per-connector status panel with **Connected**, **Last checked**, **Last event received**, **Items imported**, **Needs attention**, and **Disconnect**. Show an “as of” time on presence and availability, and an accessible source label on every imported event. Suggested user-facing states:

- `Live from Ludex` for an action recorded directly by the user.
- `Received just now from Plex` for an incoming push event, with receipt time visible.
- `Steam checked 2 min ago` / `Trakt checked 9 min ago` for snapshots or polling.
- `Sync delayed` when retries exceed the connector’s expected interval.
- `Needs reconnection` after expired/revoked credentials.

These are labels, not guaranteed timing targets; choose exact stale thresholds from real telemetry. In the feed, default to meaningful stable events: episode marked watched, film logged, game achievement observed, playthrough marked complete. Current presence is a separate optional shelf (“friends playing now”) with individual hide controls and a short expiry. Do not publish every play/pause/progress heartbeat; fold playback into a single session card, then publish a completion only when the source gives a reliable watched state or the user confirms it.

Spoiler gating must apply before writing notifications, generated captions, search indexes, previews, AI/RAG context, and shared collection summaries. For TV, compare an event's explicitly scoped episode requirements against each recipient's confirmed watched episode set; skipped episodes must not be treated as seen just because a later episode was logged. For games, hide secret achievement names/descriptions and any story milestone beyond the recipient's explicitly selected progress. If progress is unknown, show a generic “earned an achievement” card or hide it; do not infer story order from playtime.

## Build and validation sequence

1. Implement Ludex-owned manual logs, per-title progress rules, undo/edit, source provenance, and a private-by-default activity switch.
2. Build Trakt account linking with PKCE, history preview, ID matching, incremental last-activity sync, duplicate protection, history corrections, and explicit feed publishing. Confirm current developer registration and policy fit.
3. Build Steam identity + visible library/recent activity + achievements as snapshots. Test public/private profiles, hidden game details, free-to-play games, DLC/editions, deleted games, repeated replays, achievement revocation, and the real Web API response for unlock timestamps before promising dates.
4. Add a Plex webhook pilot with a real server and account, then test reachable/unreachable callbacks, retries, duplicate events, stop/near-completion thresholds, episode matching, and playback-position handling. Keep a user-facing health log.
5. Add Kodi via Trakt’s supported addon. Evaluate a Ludex local companion later if enough users want direct player presence.
6. Run a limited Xbox access spike: register a test website app, complete Microsoft sign-in/XSTS, read only the consenting account’s achievement list, inspect privacy/error behavior, and get policy clarification if production terms/access remain unclear. Do not ship session-cookie reverse engineering as a substitute.
7. Select streaming provider data only after country coverage, deep links, commercial license, image/metadata rights, storage/cache limits, and refresh cadence have written answers. TMDB and Watchmode serve different legal and deep-link needs; keep the provider behind an adapter so Ludex can change suppliers.

A successful integration should be judged by more than a green “connected” badge. Verify real consenting test accounts across privacy settings, compare provider reports to manual ground truth, measure event receipt delay/duplicates/missed events, test correction and deletion, and document the exact fields that the production account can read. No such runtime checks were performed for this report.
