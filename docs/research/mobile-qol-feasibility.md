# Ludex mobile quality-of-life feasibility

**Checked:** 2026-10-06
**Product context:** mobile app first, companion website; first audience is friend groups into TV and PC gaming; account connections plus optional extension/desktop companion.

## Recommendation

Make **share to save**, **one-screen quick logging**, **links that reopen the same item on web or app**, and **offline-safe manual actions** part of the first usable mobile loop. Use mobile for quick capture and social response; keep provider polling, reconciliation, and durable event fan-out on Ludex’s backend. Add home widgets after the basic flows work. A Live Activity should be a user-started shared session/timer experiment, not a promise to mirror arbitrary playback or game telemetry.

The platform capabilities below are documented. The Ludex flows are product recommendations. No native implementation or device test has been performed.

## Flow and platform fit

| Flow | Platform capability and product use | Ludex decision / boundary |
|---|---|---|
| **Share to save** | iOS Share Extensions can receive the originating text plus attachments such as links, images, or video. Android `ACTION_SEND` receivers can accept declared text and image MIME types; the user confirms/edits content. [Apple Share Extensions](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Share.html) · [Android receive shared data](https://developer.android.com/develop/ui/compose/sharing/receive) | User shares a streaming title URL, store/game page, or image into Ludex. Resolve against catalog candidates, show poster/title/platform and confidence, then offer **Add to watchlist / backlog** or **Log**. Do not infer that a shared page proves the user watched or played it. Keep paste/search as fallback. |
| **Expo share intake** | Current Expo docs describe incoming share configuration for an iOS Share Extension target and Android intent filters, but label incoming-share functionality experimental; the iOS path has a documented implementation caveat. Expo Go does not support arbitrary custom native code. [Expo Sharing](https://docs.expo.dev/versions/latest/sdk/sharing/) · [Expo custom native code](https://docs.expo.dev/workflow/customizing/) | Treat Expo’s API as a candidate, not a guaranteed drop-in. Prototype URL and image intake on real iOS and Android devices before making it a launch dependency. If it fails the reliability bar, use platform targets via native code/config plugin or ship paste/link capture first. |
| **Return through links** | iOS Universal Links associate Ludex’s website with its app. Android App Links add verified domain association through `assetlinks.json`, letting an installed app open an HTTPS link while the site remains the fallback. [Apple Universal Links](https://developer.apple.com/documentation/xcode/allowing-apps-and-websites-to-link-to-your-content) · [Android App Links](https://developer.android.com/training/app-links/about) | Use canonical HTTPS URLs for title, episode, game, achievement, profile, invite, and feed item. The app and website should land on the same item. Preserve the destination through sign-in, then resume it. Validate IDs and authorization server-side; never put session secrets in links. |
| **Quick log** | Apple App Intents expose app actions to Shortcuts/Siri and support system surfaces; WidgetKit supports glanceable widgets and quick actions. Android provides launcher/home widgets, with interaction and update limits. [Apple App Intents](https://developer.apple.com/documentation/appintents/app-intents) · [Apple WidgetKit](https://developer.apple.com/documentation/widgetkit/widgets-and-complications-collection) · [Android widgets](https://developer.android.com/develop/ui/compose/glance/create-app-widget) | First release: persistent in-app **Log** button, recent items, one-tap episode completion, session start/stop, and milestone form. Add platform widgets for current activity and a quick-add entry point later. Require undo for accidental progress and a spoiler audience choice for milestone posts. |
| **Offline capture** | The OS offers bounded background work, not an always-running app guarantee. Apple schedules refresh/processing tasks when the system chooses; Android WorkManager work may be deferred, interrupted, retried, and is not guaranteed at an exact periodic time. [Apple background strategy](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app) · [Android WorkManager/data transfer](https://developer.android.com/develop/background-work/background-tasks/data-transfer-options) | **Product design:** write manual actions to a durable local outbox immediately; render them optimistically with a “Waiting to sync” state; retry idempotently when the app is active/network is available; show conflict/errors and allow correction. Give each action a stable client ID. Preserve occurrence time and date precision separately from backend acceptance and synchronization versions; delayed offline uploads must not masquerade as live activity or overwrite newer corrections. Measure queue age; do not silently drop it. |
| **External progress sync** | iOS background work is system-scheduled; Android periodic work has approximate timing, not a punctual alarm. Doze can defer ordinary work. [Apple Background Tasks](https://developer.apple.com/documentation/backgroundtasks) · [Android Doze](https://developer.android.com/training/monitoring-device-state/doze-standby) | Poll Steam/other connected providers from Ludex’s backend on a provider-specific cadence. Mobile sync should refresh the local projection when opened, and may request eligible background refresh as a convenience. The backend connector remains the source of imported events; phone wake timing is never the sync SLA. |
| **Friend push** | iOS requires notification authorization for alerts/sounds/badges; users can change it later. Android routes deep links from notifications through app links/intents. [Apple notification permission](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications) · [Android deep links](https://developer.android.com/training/app-links/create-deeplinks) | Ask after the user follows friends or chooses notification settings, with categories (friend activity, replies, invites, sync issues), per-friend mute, quiet hours, and digest controls. Push a compact event pointer; on tap, open the relevant feed item and fetch current permission/spoiler-safe content. Never make push delivery the persistence mechanism. |
| **Live Activity / ongoing status** | ActivityKit supports user-visible, time-bounded activities, including remote updates; the system can throttle frequent pushes. A Live Activity’s isolated view cannot fetch its own network data. [ActivityKit](https://developer.apple.com/documentation/activitykit) · [ActivityKit push update guidance](https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications) · [Live Activity data limits](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities) | Consider only an explicitly started Buddy Run/watch-party session with a stop control and shared audience—not passive “is online/watching/playing” telemetry. Don’t promise second-by-second provider progress. Start/authorize the activity under platform rules, push only meaningful changes, and retain in-app state as canonical. |
| **Widgets and shortcuts in Expo** | Expo’s current `expo-widgets` documentation describes **iOS** widgets and Live Activities and says it requires a development build. Android widgets are a separate Android widget target/API. Expo config plugins can add extension targets and native configuration; local Swift/Kotlin modules can bridge app actions. [Expo Widgets](https://docs.expo.dev/versions/latest/sdk/widgets/) · [Expo app extensions](https://docs.expo.dev/build-reference/app-extensions/) · [Expo config plugins](https://docs.expo.dev/config-plugins/introduction/) | Do not promise one Expo widget implementation works on both platforms. Budget native build/release work and separate iOS/Android device validation. Expo Go is not the acceptance environment for extensions/widgets. Keep this as a later polish milestone unless a device prototype shows low maintenance cost. |

## First-release sequence

1. Canonical HTTPS routes and verified app association, with website fallback and post-login return.
2. Manual quick log backed by a durable local outbox, optimistic UI, correction/undo, and privacy/spoiler controls.
3. Share-to-save for URLs first; confirm catalog matching before adding. Prove image share separately because payload formats vary by sender.
4. Push categories and deep-linked feed notifications, with permission requested in context.
5. Native widgets, App Intents/shortcuts, and Live Activities only after the app has real daily use and platform builds can be validated.

## Acceptance checks before claiming these integrations work

- Share URLs and images from representative browser, streaming, and game-store apps on physical iOS and Android devices; include cold start, warm start, duplicates, unsupported content, and cancel.
- Tap title/profile/invite/feed links while installed, uninstalled, signed out, and signed in; verify app/site fallback and correct return after authentication.
- Log offline, force-quit/reopen, regain network, and confirm one event appears once on the account and only to its allowed audience. Test edits, retries, and two-device conflict resolution.
- Deny/revoke push permission; verify core feed still refreshes in-app and notification settings explain the state.
- Test notification delivery as best effort and background sync under low power, restricted background refresh, and Doze. Report provider polling delay separately from app UI latency.
- Validate each widget/extension target in release-like builds; a successful JavaScript or Expo Go run is not evidence that native sharing, widgets, or shortcuts work.
