# Go backend hosting and database notes

**Checked:** 7 October 2026. This is a documentation review for the proposed Ludex backend, not a deployment or subscription quote. No credentials or local deployment configuration were inspected.

## Azure Container Apps

- A Consumption container app can set its revision minimum replica count to `0`; the documented default is already `0`. HTTP scale rules can add replicas based on concurrent requests, and the documented default threshold is 10. The platform calculates the HTTP request signal every 15 seconds from requests over that interval. A zero minimum permits scale-to-zero and therefore a cold start on a request that arrives while no replica is running; startup latency depends on the image and application, so the docs do not support a fixed cold-start promise. [Scale rules and limits](https://learn.microsoft.com/en-us/azure/container-apps/scale-app#scale-definition)
- Container Apps Jobs are the matching primitive for finite work. A job can start manually, on a schedule, or from an event; scheduled jobs use a cron expression. It can use the same environment and image as the API while running a separate command. [Jobs](https://learn.microsoft.com/en-us/azure/container-apps/jobs)
- Consumption resource use is metered per second by allocated vCPU-seconds and GiB-seconds. The published monthly free grant is per Azure subscription: 180,000 vCPU-seconds, 360,000 GiB-seconds, and 2 million external HTTP requests. Apps scaled to zero incur no compute usage; jobs consume active-rate CPU and memory while each execution runs, and jobs have no HTTP request meter because they have no ingress. The API and jobs share the subscription resource grants; the grant is not a separate allowance per app. [Billing](https://learn.microsoft.com/en-us/azure/container-apps/billing)
- As a scale illustration, if a replica is allocated 0.25 vCPU and 0.5 GiB throughout its active time, each of the CPU and memory grants corresponds to 200 replica-hours before other Consumption resources on the subscription use those grants. This is arithmetic from Microsoft's published units, not a forecast of Ludex's bill.
- Dedicated workload profiles are a poor fit for a strict low monthly target unless there is a specific need: billing is based on allocated profile instances, and having a Dedicated profile incurs a management fee in addition to variable instance cost. Microsoft's billing page also flags private endpoints and planned maintenance as features that can incur a Dedicated Plan Management charge even in an otherwise Consumption environment. Other Azure resources and a customer virtual network can add charges. [Billing](https://learn.microsoft.com/en-us/azure/container-apps/billing)
- Therefore, a Consumption API plus low-frequency scheduled Consumption Jobs can fit a small budget more naturally than an always-on or Dedicated service, but official docs alone cannot verify a US$10 ceiling. Region-specific rates, active replica/job time, logging, networking, registry/storage, other subscription usage of the grants, and any existing credits all affect the result. Use the Azure pricing page/calculator with the chosen region and actual allocated sizes; compare metered resource cost before and after credits. [Azure Container Apps pricing](https://azure.microsoft.com/en-us/pricing/details/container-apps/)

## Supabase PostgreSQL with Go and pgx

- Supabase's connection guide recommends the direct connection for a persistent backend when its network supports IPv6; for an IPv4-only persistent backend it recommends the shared pooler in session mode. The shared pooler's transaction mode is an option for short-lived/serverless connections and uses port 6543. [Connection choices and client settings](https://supabase.com/docs/guides/database/connecting-to-postgres)
- Supabase explicitly says transaction mode does not support prepared statements and instructs clients to turn them off. It also lists transaction-scoped limitations: session state does not persist between transactions, cursors must stay within one transaction, and query pipelining is unsupported. This is the decisive compatibility constraint for pgx. [Transaction mode limitations](https://supabase.com/docs/guides/database/connecting-to-postgres#transaction-mode-limitations)
- pgx uses protocol-level named prepared statements by default. Its documentation says `QueryExecModeExec` is compatible with PgBouncer when prepared-statement support is disabled; it also cautions against `QueryExecModeDescribeExec` in transaction pooling. For Supavisor transaction mode, configure pgx's `DefaultQueryExecMode` as `pgx.QueryExecModeExec` (or select an equivalent no-prepare mode) and avoid session-state assumptions. Do not rely on pgx's generic note about PgBouncer 1.21+ to infer Supavisor's capabilities; Supabase's own transaction-mode guidance says prepared statements are unsupported. [pgx v5 PgBouncer guidance](https://pkg.go.dev/github.com/jackc/pgx/v5#hdr-PgBouncer)
- pgx is a pure-Go PostgreSQL driver/toolkit and includes an adapter for `database/sql`; its native pool is `pgxpool`. Reuse a pool per API process, size it explicitly, and account for the sum across the maximum API replicas so scaling does not multiply connections past the Supabase pool/database limit. [pgx README](https://github.com/jackc/pgx#readme), [pgxpool](https://pkg.go.dev/github.com/jackc/pgx/v5/pgxpool)
- sqlc officially supports the `pgx/v5` generated-code target (since sqlc v1.18). It generates typed methods from SQL and can use native pgx types, so it is a compatible pairing rather than a requirement to route Go through Prisma or `database/sql`. [sqlc: Using Go and pgx](https://docs.sqlc.dev/en/latest/guides/using-go-and-pgx.html)

## HTTP routing choice

- Go 1.22's standard `net/http.ServeMux` added method-aware patterns and named path wildcards (available through `Request.PathValue`). That covers ordinary versioned JSON API routes without a third-party router. Check the Go module version before relying on this behavior; earlier Go versions had different ServeMux matching rules. [Go 1.22 routing enhancements](https://go.dev/doc/go1.22#enhanced_routing_patterns), [ServeMux documentation](https://pkg.go.dev/net/http#ServeMux)
- chi remains optional: its official project describes it as a lightweight router built around standard `net/http` handlers, with composable route groups/subrouters and middleware. Use it if those ergonomics materially help route organization; it is not needed for HTTP support itself. [chi project](https://github.com/go-chi/chi)

## Implications and open items for Ludex

For the stated 100 registered accounts and roughly 10–20 simultaneous users, the account count alone does not predict ACA cost. A scale-to-zero Consumption API is compatible with accepting occasional cold starts, and independently scheduled jobs avoid paying for a polling process between runs. The actual bill still depends on traffic, run duration/frequency, resource allocation, selected region, and what else consumes the subscription-level grant. No source can validate the `$10` target or credit balance without those values and the subscription's current pricing context.

If using Supavisor transaction mode, set pgx to avoid prepared statements and cap each process's pool with the maximum replica count in mind. If choosing direct PostgreSQL access or Supavisor session mode instead, confirm ACA's outbound IP family and the Supabase endpoint mode before implementation. The Go standard library is sufficient for a modest API; chi is a maintainability preference.

The candidate Azure model deployment names (`thehub` / `gpt-6-luna` / `text-embedding-3-large`) were supplied as unchanged context and were not checked or altered in this research.
